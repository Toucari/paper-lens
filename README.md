# paper-lens

> 一条可裁剪的论文流水线：**把论文变成你能高效读完的形态，而不是替你读完。**

大多数"AI 读论文"工具都在做同一件事：你丢一篇 PDF，它还你一段摘要。问题是——摘要你信吗？它跳过了哪些段落、漏掉了哪个附录、把哪个数字读错了，你都不知道。

paper-lens 走反方向。它把机械的部分自动化（抽文本、捞结构、裁图、核数值、排优先级、记账），把**判断**留给你。设计上有个硬约束贯穿全程：**八节总结必须等你读完才做**——因为总结里最有价值的两节（你当时卡在哪、这篇值不值得用）本来就只能来自你的阅读。

---

## 三档，按你愿意投入的时间选

| 档            | 回答什么问题       | 产出                          | 你实际要做的        |
| ------------ | ------------ | --------------------------- | ------------- |
| **Quick**    | 这篇**值不值得**读  | 一页速读卡                       | 什么都不用做，5 分钟看卡 |
| **Standard** | 这篇**到底怎么做**的 | 讲解级精读稿 + 八节总结               | 自己读完精读稿，期间提问  |
| **Full**     | 这批里**哪几篇能用** | 上面全部 + 图文 HTML + 五维分 + 跨篇账本 | 参与横向判断        |

默认走 Quick。**升档由你决定**——Standard 需要你投入几小时阅读，不该由工具替你决定。

# 2. 填 profile（研究方向、场子白名单、目录）

# 3. 拿一篇已有 PDF 试链路

四步都过，就可以把 `SKILL.md` 交给你的 AI 助手（Claude Code / Cursor / 任何支持 skill 的 agent），说一句"快速看一下这篇"。

## 它不做什么

写清楚边界，比列功能更有用：

- **不替你读。** 不会在没有你的阅读的情况下产出总结和评级。
- **不猜数字。** 扫描版 PDF、抽不全的表格、OCR 会错位的数字——一律报"需人工核对"，不用推断填空。
- **不覆盖你的历史。** 历史总结文件要改，先问你。唯一会自动更新的是登记册的"最近检查"列。
- **不删你的文件。** 临时产物移到 `_trash_<日期>/`，由你自己删。

## 三条硬律

这三条不是建议，是产物的有效性前提。

### 律 1 · 数值一律回原文核

任何进入产物的数字，必须能指回**表号 / 式号 / 页码 / 代码行**。二手来源（机器翻译、别的模型的解读、其他论文的引用）全部要核。

核不了的标 ⚠️，且**不得进入结论段**。

> 真实教训：一份转录说"某模型在某数据集上等于随机"——回原文查主表，Balanced Accuracy 恰好是 `0.5000`，这条成立；另一份说"加了结构约束提升了性能"，主指标 Top-5 其实降了 0.4，只有辅助指标涨。两条都得核，否则一边冤枉、一边被骗。

### 律 2 · 读完才总结

精读稿写完 ≠ 可以总结。必须等使用者明确确认读完。

阅读期间提的问题，是八节总结第①节的素材；没提问就如实写"无问答记录"，**不许编**。

### 律 3 · 区分「没做」和「做错了」

这是最容易混、后果最严重的一处：

|         | 含义      | 落在哪 |
| ------- | ------- | --- |
| **Gap** | 该做而没做   | §四  |
| **问题**  | 做了但做得不对 | §六  |

引用时分不清这两者，等于没有引用口径。

## 六个阶段

`SKILL.md` 只做路由和硬约束，细节在 `references/`，按档位**按需加载**：

| # | 阶段 | 文档                    | 干什么                     |
| - | -- | --------------------- | ----------------------- |
| 0 | 配置 | `setup.md`            | 问答式生成 profile           |
| 1 | 找  | `01-find.md`          | 搜、验主会、按价值排序、归档、写轮次导航    |
| 2 | 解包 | `02-ingest.md`        | 校验 PDF、抽全文、**先捞节标题**、裁图 |
| 3 | 精读 | `03-read.md`          | 讲解级精读稿 + 图文 HTML        |
| 4 | 总结 | `04-summarize.md`     | 八节结构化总结                 |
| 5 | 评估 | `05-evaluate.md`      | 五维加权分、校准、登记册、批次横向       |
| 6 | 审计 | `06-leakage-audit.md` | 分数能不能当证据                |

`00-conventions.md` 是全局约定，任何档位开始前读一次。

### 为什么第 2 阶段强调"先捞节标题"

分段读 PDF 时，两个读取窗口之间会有缝隙。附录标题正好落在缝隙里，你会得出"这篇没讨论局限"的错误结论——而实际上 Limitations 就在附录 B。

**实测**：某篇论文正文写上下文长度 500、附录 A.2 写 100。只看正文会漏掉这个内部矛盾，而这个矛盾直接决定实验能否复现。

所以核结构必须先 `plens.py toc`。这是整条流水线里最容易被省掉、又最容易出事的一步。

## 脚本

一个入口，零配置，自动在 `pymupdf` / `pypdf` 之间选后端：

```bash
python scripts/plens.py init     --root DIR           # 建 papers/ rounds/ ledger/
python scripts/plens.py fetch    ARXIV_ID --venue "ICLR 2025" --title "..." [--version v2]
python scripts/plens.py text     PDF -o OUT [--pages 3,4-7]
python scripts/plens.py toc      PDF                  # 全部节标题 + 页码
python scripts/plens.py figures  PDF -o DIR [--scale 4]
python scripts/plens.py check    HTML                 # 标签闭合 / 图片存在 / 锚点可达
```

`fetch` 会对每个 PDF 做三道校验：`%PDF-` 头、`%%EOF` 尾、体积 > 10 KB。不通过就报 FAIL，不会把坏文件当成功。

## 两个账本

| 文件                       | 作用           | 解决什么     |
| ------------------------ | ------------ | -------- |
| `ledger/registry.md`     | 全量索引，一篇一行    | 解决"漏"    |
| `ledger/case-library.md` | 评分锚点，只存已打分的行 | 解决"尺度漂移" |

**为什么不能合成一个**：案例库只有评过分的行，拿它做全量清查会读不到"还没评过的论文"——而"还没评"的恰恰最需要被找出来。

## 五维评分

给"这篇值不值"一个可比较、可累积的尺度：

| 维度    | 权重  |
| ----- | --- |
| 方法创新  | 20% |
| 实证可信度 | 25% |
| 可复现性  | 20% |
| 可搬运性  | 20% |
| 严谨与诚实 | 15% |

逐档锚点在 `assets/scoring-anchors.md`。分档：≥ 4.0 = A，3.3–3.9 = B，< 3.3 = C。

**"实证可信度"问的不是结果好不好，而是"这个结果能不能当证据"。** 这一维最容易被打错——被漂亮的数字带偏。检查项包括：超参是否在测试集上选、划分粒度是否声明、消融是否只动一个变量、基线数字是自己跑的还是引用的、有没有显著性检验。

另外两条容易被忽略的规则：

- **用"差值 ÷ 合并标准误"判断差异，不要看点估计。** 两个配置 0.5758 vs 0.5337 看着差 0.04，算下来只有 1.2 个标准误——在噪声内，只能说"无法区分"。
- **同一张消融表，不同指标的最优配置可能不同。** 别只挑一个指标宣布"最优配置"。

## 关于「快速阅读」的一个取舍

Quick 档只有 15 分钟预算，所以它**不抽图、不建 HTML、不打分、不写八节**。

但它**仍然要求核数**——速读卡上的每个数字也要能指回表号。快不等于糊。

## 这套东西是怎么来的

不是设计出来的框架，是从一个人的真实工作流里长出来的——读了二十多篇论文之后，反复踩坑、反复修改，才稳定成现在这七份文档。

因此它有一些特征可能和通用工具不太一样：

- **规则写得很硬**（"必须""不得""不许"），因为软性建议在实际使用中会被跳过。
- **每条规则背后基本都有一个踩过的坑**，文档里尽量把坑写出来，而不是只写结论。
- **保留了失败模式清单**。知道什么会出错，比知道正确做法更有用。

如果你在用的过程中踩到新坑，改文档，别绕过它。

## 适用 / 不适用

**适用**：需要真的读懂并记住一批论文；要判断"这篇能不能用"；要写综述或做选型；需要跨时间保持评价尺度一致。

**不太适用**：只想快速知道一篇论文的结论（那用普通摘要工具更快）；论文本身是扫描版且无文本层；纯理论论文（第 6 阶段用不上）。

## 维护与更新

**持续迭代项目，不定期更新，不承诺版本节奏。** 用得越久、踩的坑越多，它才越像样。

每次改动都记在 `CHANGELOG.md`：改了什么、为什么改、被哪次实测或哪篇论文触发。**改锚点会让历史分数整体漂移**，这类改动尤其要留痕。

### 欢迎反馈

**最有价值的反馈是「这一步根本做不到」，而不是「再加个功能」。**

具体包括：某条规则在你的领域里不成立；某个脚本在你机器的 PDF 上崩了；某句话你读不懂所以跳过了；某个字段你从来没用上。这些比功能请求有用得多——文档里的每条硬规则背后基本都有一个踩过的坑，**你知道什么会出错，比知道正确做法更有用。**
